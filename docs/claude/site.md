# The site: text, pages, search and deployment

Part of the project's notes: `CLAUDE.md` is the short core, loaded in every session, and this file holds one topic. It was moved here from `CLAUDE.md` as it stood on 2026-11-08; new notes on this topic go here.

The rule for the site's text (`VOICE.md`, `DESIGN.md`) and the deployment's limits are in `CLAUDE.md`.

## Home page

**Šta je novo**: the home page's news under the three doors (`components/HomeNews.tsx`, headed "Dopune" since 2026-11-04) is `website/app/data/news.ts`, newest first: the last three items with a title (the big changes) and four without (a line each), in Serbo-Croatian, Slovene, Macedonian and English (the Cyrillic is made from the Latin). Changes of a few days may stand as one. Each says what a visitor notices, plainly and once, with a count only where it helps: no bracketed examples, no lists of units, no words of the pipeline ("nominativ", "u padežu", GeoNames, "zapisima koji već postoje"; the user found them reading as generated text, 2026-10-27). Older news has no page yet, so there is no button for it.

**Icons and the share image** (`public/favicon.ico`, `icon.svg`, `apple-icon.png`, `og.jpg`: a white star on Partisan red, and the home band's photo in the red for link previews) are made by `python scripts/make_site_icons.py`. The metadata (`app/i18n/metadata.ts`) takes the site's address from Vercel's `VERCEL_PROJECT_PRODUCTION_URL`, so canonical, language and preview links are absolute. An unknown address gets `app/global-not-found.tsx` (the site has two root layouts, so it is `experimental.globalNotFound`), which reads the language from the address in the browser.

## Languages

**Languages.** The site is in Serbo-Croatian at the plain addresses (/, /units/<id>, /izvori, /galerija, /kartica), in Serbo-Croatian Cyrillic under /sr-cyrl, and in Slovene, Macedonian and English under /sl, /mk, /en (`app/(sr)/` and `app/(intl)/[lang]/`, two root layouts; both render the same pages from `app/views/`). Components never hard-code text: they take it from `useT()` (client) or `messagesFor(lang)` (server), from `app/i18n/messages/<lang>.ts`; `sr.ts` sets the keys, and the type check fails when another language lacks one. Each language is written for its readers, not translated word for word (`VOICE.md`, "Other languages"). The Cyrillic version has no text of its own: `messages/sr-cyrl.ts` is `sr.ts` written letter for letter in Cyrillic (`app/i18n/cyrillic.ts`), as are the unit cards and book descriptions, so a change to the Latin text shows in both scripts; strings a message function is given (a query, a name, a book title) stay as they are. Links inside the site go through `useLocalePath()` / `localePath()` so they stay in the page's language. The language menu in the header (`components/LanguageMenu.tsx`: a globe with the page language's code, beside the light/dark switch) offers the languages in `FINISHED_LANGS` (`app/i18n/config.ts`): add a language there once its text is finished and read through; until then its pages build at their address for checking, unlinked and kept out of search engines. A page loads only the text of the languages it may be in: each root layout gives `SiteShell` its provider (`SerboCroatian` in `i18n/LangContext.tsx` for the plain addresses, `i18n/AnyLanguage.tsx` for the others), so client components read the text through `useT()` and a unit's name and card through `useUnitText()`, never `messagesFor` or `i18n/units.ts`, which hold every language (the server's pages may). A new unit needs its name and card in `app/i18n/units.ts`, a new book its description in `app/i18n/sources.ts` (the titles' parts and authors the dialog shows are in `i18n/sourceNames.ts`), in all three languages; the build warns about any that are missing (they fall back to the Serbo-Croatian text). Emails from the site's forms stay in Serbo-Croatian and name the visitor's language.

## Unit Photos

A unit's card photo must show a group of that unit's own soldiers, and the photo's description must name the unit. They come from the znaci.org photo gallery; `docs/UNIT_PHOTOS.md` lists each photo's source and description, plus which units have none that qualifies. When adding a unit, add it to `UNITS` in `scripts/find_unit_photos.py` and run `--candidates <key>`. It lists every photo tagged with or captioned for the unit, with contact sheets and the museum caption cards of photos that have no typed description. Then set `photo` and run `--apply <key>`. If the gallery has nothing, the unit's own book on znaci.org often has captioned photos: `--book <key> 00001/267.pdf` lists each photo with the caption printed under it (set `book=` instead of `photo`). Many site photos from before this rule turned out to be other units (`--identify` matches site images against the gallery). The cards, the band and the unit page load smaller copies of each photo (`public/images/w640/`, `w960/`, `w1280/`, through `lib/unitImage.ts`): after adding or changing a unit photo, run `python scripts/make_unit_image_sizes.py`.

## Band Posters

On wide screens (1400px and up, where the margins can hold them) the home band's margins carry the Partisans' own wartime posters, pasted like a wall: drawn over the band at 15% so that their pale paper shows faintly, and fading towards the column (`components/BandPosters.tsx`, inside `BandPhoto`). There are 14 walls (`data/bandWalls.json`, written by `scripts/make_band_walls.py`, the user's choice of 2026-11-05 from 17 on a page of mockups, leaving out 13, 14 and 17): a page load shows one at random, never the one the last load showed (`localStorage`), and it stays until the page is reloaded: nothing changes while someone looks, and moving between the site's pages keeps it (the user's decision of that day, after trying a change every 30 seconds). Every wall has one structure, the only one the user accepts (two rows on each margin, every poster 178 px high, about 10 px of overlap, a slight tilt, `ROWS`, `GAP`, `WOBBLE`); only the posters and their order differ, so a new wall is a new list of posters, never another size or overlap. The band is 287 px high on a 1920 screen, so the lower row is cut by its bottom edge and about 10 posters show; the outer ones need a wider screen. The 38 posters are those the user ranked 1 or 2 on a ranking page, or ranked 3 with a warm comment, each with what the user's comments ask (no. 14's text cut by the lower row, 16, 19 and 51 towards the edges, `domovi-sume` a little brighter, `BRIGHTER`); posters with swastikas or grotesque caricatures stay out, except `nov-izdajalce`, which the user ranked 1. Below 1400px nothing shows or loads: neither the walls' data nor a print. `scripts/make_band_posters.py` makes the prints in `public/plakati-band/` from the local `plakati/` (the user's copies, the Wikimedia Commons originals, their 960-px copies and the 500-px copies in `novi/thumbs/`) and removes any print not in its `BAND`. The other mockups (dark and light ink, mosaic, lettering alone), kept for later work, are local too: `/predlog/plakati`, `public/plakati-mockup/`. Commons tags the posters public domain, but several of the named artists died after 1955 (Kun, Mraz, Mujezinović, Mihelič, Prica, Kristl, Murtić, Jakac, others of the new posters unknown), so life-plus-70 copyright may still cover theirs: unchecked, and the site credits the posters nowhere yet.

## Medals

A soldier whose entry (or a merged entry) says "narodni heroj" ("proglašen za narodnog heroja", "Ordena narodnog heroja"; not "predložen za narodnog heroja") gets the Orden narodnog heroja, and one whose entry names the "spomenica" gets the Partizanska spomenica 1941 (`decorationsOf` in `website/app/lib/records.ts`); a woman's entry that names a relative's title is not hers (2026-10-28: "sestra Ljubica proglašena narodnim herojem", "Otac, narodni heroj Jugoslavije", the 5. proleterska's women and two of the 12. slavonska's, 18 in all): hers is a hero book's entry, the feminine ("proglašena") in a sentence that names no relative, or a mention in a sentence that names no relative and no man ("koji", "proglašen", "poginuo"), nor does the one before it ("Narodni heroj.", "Odlikovana Ordenom narodnog heroja"). Search results and "Na današnji dan" show the engraving (`gravira`, drawn in the text colour); the soldier popup and the Spomen-kartica show the photograph (`foto`), hanging from the red rule under the unit photo, with "Narodni heroj · Nosilac Partizanske spomenice 1941" under the unit. The images in `website/public/medalje/` are made by `scripts/make_medal_images.py` (needs `pip install potracer`) from a Commons photo of the order (Pinki, CC BY-SA 4.0, credited on the Izvori page) and the WIPO register's image of the spomenica (public domain).

## Map and unit pages

**Map and unit pages** (in git since 2026-10-17, on the site but not linked from it, `robots: noindex`; their text is still written in the pages, Serbo-Croatian only, and moves to the messages before they are linked):
- `/mapa` (`app/(sr)/mapa/`) is the 1941 map in the style of the books' sketches.
  - It shows the war paths of the Prva lička, the Prva proleterska and the 3. krajiška (`units/<key>.ts`, from `scripts/make_unit_route.py` and each brigade's book), the occupation zones by period (`scripts/make_map_1941.py`, `trace_ndh_zones.py`) and the liberated territory month by month (`scripts/trace_liberated.py`).
  - The liberated territory is traced from the 1952 *Istoriski atlas* as photographed by the Hrvatski povijesni muzej, whose catalogue reserves all rights; settle that before linking the map.
  - `?jedinica=<key>` opens one unit with no switch to another (`UNIT_PAGES` links back to its unit page).
  - `/mapa/spisak` lists the fallen a count stands for.
- `/mapa/igman` (2026-10-30, the user's wish) lists the Prva proleterska's men in the column that crossed Igman on the night of 27-28 January 1942, by battalion, with filters (an entry names the march or the frostbite; died after the march; fell later in the war; lived through it). Who was in the column is Vuksanović's monograph (the cached znaci 00003/382, its chapter "Igmanski marš": the 1., 2. without its 3. četa, 5. without its Užička četa, the 3. and the staff and sanitet; the 4. and 6. bataljon were elsewhere), each man's battalion and company his place in the Rudo line-up of 21 December 1941 (its parser run into `data-extraction/.cache/igman/rudo.json`, matched by the entry's place on the page), less those who fell before the march (Pjenovac, Bijele Vode); the Posavska četa of the 6. listed apart as probable, and of the men who came later only those an entry names on the march. `python scripts/make_igman_list.py` writes `app/(sr)/mapa/igman/igman.json` (664 men on that day; run it again after the Prva proleterska's records change). Making it found one man with two records, Maksimović Borisava Petar "Mali Perica" (merged, 290160). Each man's record dialog and memorial card say it in a line under the facts (the user's wording of 2026-10-30): "Kao pripadnik 2. čete 1. bataljona, učestvovao je u Igmanskom maršu 27–28. januara 1942." ("pripadnica", "učestvovala" for a woman, `isWoman`), "najverovatnije je učestvovao" only for the Posavska četa, whose place in the column the book doesn't give, and "Učestvovao je u Igmanskom maršu ..." where only his entry names it; never a medal, since the march was no decoration. `scripts/make_war_events.py` writes each man's events to `website/data/events/<unit data file>` (`WarEvent` in `lib/types.ts`: `e`, `sure`, the company and battalion or the section; the Igman ones from `make_igman_list.build()`), `scripts/prepare-data.ts` merges them into his record as `events` (as the life events; the dev server watches the folder), `lib/warEvents.ts` makes the lines with `t.record.igman` and `t.record.sutjeska` in each language. The same day the battle of the Sutjeska got its line, "Učestvovao je u bici na Sutjesci, maja i juna 1943." (the user's "do the same for sutjeska"): every record holding an entry of Kučan's Borci Sutjeske, its own, merged in or a linked record's in another unit (24,666 in 80 units: the book is the roll of everyone in the battle, so it is always sure and names no company). Run `make_war_events.py` after the units' records change (a merge, a link, a unit), as `build_relations.py`; a new event is another `e`, a rule in the script and a message.
- `/mapa/bataljon` is the 2. bataljon of the Prva lička, its fights step by step on terrain sheets (`bataljon/episodes.ts`, `scripts/make_battalion_map.py`). Anything the book does not state is marked as the map's estimate.
- `/jedinica/<id>` is a unit's overview, the Prva lička alone so far (`app/(sr)/jedinica/`):
  - its path as lanes (names, commands, battalions) and dated events;
  - doors to the map, the staff (`/stab`), the battalions (`/bataljoni`, a page each: staff, companies, platoons, soldiers) and the soldiers list;
  - its data is `_data/<id>.ts`, written by hand from the unit's book and its entries, and `_data/<id>.posts.json`, the posts the unit's own entries name (`scripts/make_unit_overview.py <id>`).
  - The pages are built with the site (`generateStaticParams`): they read the unit files at build time.
- `/sastav` stays local (excluded in `.git/info/exclude`).

## Search, data files and a record's own address

- **Search runs on the server**: the home page asks `app/api/search/route.ts` (a Vercel function, region fra1) for one page of results at a time; it runs `lib/soldierSearch.ts` and `lib/searchFilters.ts` over `website/search-data/`. Vercel caches each answer until the next deploy. The filters there are answered from arrays built with the data (`filterTest` in `lib/searchData.ts`: each soldier's place-filter text, birth year, death type), so a change to `applyFilters` must be made there too. A new unit needs nothing extra. Unit pages ask it too, for their unit alone (`?u=<unit id>`): their first page is in the page itself. The same route answers a record's kin (`?u=<unit>&kin=<id>`, `kinPage`: the record found by its id or a merged or linked entry's, the records before and after it in the unit's list, his sub-unit's soldiers at each level and those who fell the same day, rows without the entry text), which the dialog asks for its previous/next and comrades tree, a unit page for a link to one record (`?borac=`), the Spomen-kartica for its record; and some records' rows by id (`&ids=`, `rowsPage`: the map's list of the fallen). There is no in-browser search any more (2026-10-28): when the route doesn't answer, the page says the lists didn't load. The function runs in Frankfurt: `website/vercel.json` (`regions`; Vercel ignores the route's `preferredRegion`). The project's Root Directory on Vercel is `website/`, so a `vercel.json` at the repository root is not read.
- **The birth-year filter** (2026-11-19, a visitor's wish passed on by the user): a year with ±0, ±2 or ±5 keeps only records whose `birth_year` falls in it, so the many entries that print no year drop out. Beside the year and its menu, "+ bez godine rođenja" (`SearchFilters.tsx`, its own `SearchFilters.module.css`, so globals.css isn't touched; greyed until a year is typed) keeps them too, and is on unless pressed off (the user: it "should be automatically selected"; genealogy sites keep a record without the year and rank it lower): `withoutYear` is true in `NO_FILTERS`, and the address says only the strict choice, `&bezgodine=0` (an old link's `&bezgodine=1` is the default anyway). They are listed after those born in the range, among the names found and again among the similar ones; the user chose it, no. 4, among eight mockups (`admin/mockups/filter-godina.html`, admin-panel branch), after a tick box and a link in the results line alone didn't do. The results line also says how many the year left out, as a link ("Pronađena 83 borca · još 273 bez godine rođenja"), counted among the names found only, so it adds up, and once they are in, "od toga 273 bez godine rođenja (skloni ih)"; a year that finds nobody with a year offers them in the empty message. The server counts them (`undated` in the answer, `searchData.ts`). `applyFilters` in `searchFilters.ts` has the same rule but nothing calls it now.
- **"Cela strana izvora"** (2026-11-19, the user: "messy and redundant and confusing"): the fold holds the page and nothing else. The entries, each book's, are under "Reference" above it (`EntryStrip`), so the fold no longer repeats them as text with a "još N zapisa" fold of its own; the book and page are named once when it is open, in the viewer's top line (the book menu with several scanned books), the grey line under the fold's title only while it is closed.
- **Data files** (2026-10-28): `website/scripts/prepare-data.ts` (`npm run prepare-data`, bundled by esbuild) writes from the unit files what the pages load: each unit's full records in parts of 250 with their life events (`/data/records/<unit>/<part>.json`), "Na današnji dan" (`/data/on-this-day/<MM-DD>.json`), the margins' portraits' soldiers, the places index's small files (all in `website/public/data/`, `lib/dataFiles.ts`), the search's data (`website/search-data/`), and what the pages read while they are built (`website/generated/pages.json`: each unit's count, the Galerija's portraits; `lib/generated.ts`); all gitignored. It writes only what changed (a unit's records when its data file or life events change; the rest when any unit, places.json, vez-sets.json or the script's own code does; `--force` everything; `generated/manifest.json` keeps what it wrote from). `npm run build` runs it first, so Vercel's Build Command must stay `npm run build`, or the site has no data and the search answers 503. Under `next dev` the server runs it on start and again a few seconds after a data file changes (`instrumentation.ts`, `lib/devData.ts`): a dev server started anywhere (the main checkout's :3000, a worktree's :3001) keeps its own checkout's files current, in a process of its own, so the dev server never holds every unit's data (it held 3-7 GB when each data route parsed all units). A fresh checkout's first run takes a few minutes; until it ends, records, "Na današnji dan" and search are missing there. The unit files themselves (`public/*.json`) are never served (2026-11-16): no page loads them, and the live site handed `/ostali-borci.json` (53 MB) to anyone who asked, every unit's records at once on the site's bandwidth; `website/middleware.ts` answers them 404, its matcher (`soldiers.json`, `*-soldiers.json`, `ostali-borci*.json`) keeping every other address away from it. A unit file named otherwise would be served: keep to the pattern.
- **A record's own address** (2026-11-04; the user's "make sure it will not overload vercel"): `/borac/<id>`, `/en/borac/<id>` (`recordPath(id, lang)`), and the older `/units/<unit>?borac=<id>` still opens the record. `app/(sr)/borac/[id]/route.ts` and its `(intl)` twin call `lib/recordAnswer.ts`, which renders nothing: it reads three static files from the site's own CDN (`/data/where/<first 7 digits>.json`, written by `prepare-data.ts`, which says each id's unit and slice, and for an id merged away its keeper, answered with a 308; the slice; the one prerendered page `/borac`, `views/RecordPage.tsx`) and writes the record's title, description, preview tags and text into that page, so a shared link's preview and a reader without scripts have them; the page then opens the record in the dialog, and closing it goes to his unit. The CDN keeps each answer until the next deploy (`s-maxage`), so an address runs the function once per deploy. If anything fails it answers a 307 to the older address. Measured 2026-11-04 on the real files: about 2 ms of its own work, 34 KB (6.5 KB compressed) out, 26 KB in; on Pro's Frankfurt prices a crawler reading all 509,000 uncached costs at most about $9, far less in the id order a crawler walks (an instance keeps 8 slices). Keep it so: **a link to a record is a plain `<a>`, never `next/link`**, whose prefetching would run the route for every record in sight (it answers a prefetch with a 204 in case one slips in); never read the search's data or render a PDF there (so the preview picture is his portrait or the site's `og.jpg`, not a crop). `public/robots.txt` (the site's first) keeps every crawler off `/api/` and all but the link-preview bots off `/borac`, and the answer says `X-Robots-Tag: noindex` (`NOT_INDEXED`): names are not findable from Google until the user decides; to open it, take those lines and that header out and add sitemaps in batches, watching Usage. Opening a record in a list pushes this address (`lib/useBackClosesRecord.ts`), stepping through records replaces it, Back or the X takes it off. The shell has no title or preview of its own (`RECORD_SHELL_METADATA`), else React puts them back as it loads.
- **Visitors** (2026-11-18, the user's Reddit post): Vercel Web Analytics, on the project's Analytics tab (visitors, pages, referrers). `@vercel/analytics`'s `<Analytics />` sits in `SiteDocument` (`components/SiteShell.tsx`), so every page in every language and the 404 page have it; cookieless, its script and its counts on the site's own address (Vercel gives the project a path of its own, `/4c85822f9793765c/script.js` and `/view`, not `/_vercel/insights/`, so a check of the HTML for "insights" finds nothing: the script is added in the browser), so the CSP needs nothing. It renders only when `process.env.VERCEL === '1'` (a build made on Vercel): locally that address doesn't exist, and under `next dev` the package would load a script from va.vercel-scripts.com, which the CSP refuses. It counts from its first deploy on; Observability's CDN requests count files, not people.
